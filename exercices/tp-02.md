# TP 2 — Premier appel structuré à un LLM en Java et lecture de l'usage tokens

> Module : 2 — Bases de l'IA générative textuelle (LLM, Transformers, RAG)
> Durée estimée : 1h00
> Difficulté : 2 / 5
> Type : Travaux pratiques guidés
> Langage : **Java** — à partir de ce TP, tout le code de la formation est en Java (projet Maven `~/formation/java`)

## Mise en situation

Vous savez maintenant ce qu'est un token et un embedding. Il est temps de faire votre **premier appel à un modèle de langage** de façon propre et réutilisable — et en Java, votre langage de filière. En production, un appel LLM n'est jamais « envoyer une chaîne et afficher la réponse » : on veut un *résultat structuré* (texte + modèle + usage tokens), on veut une couche d'accès unique réutilisable, et on veut toujours savoir ce que l'appel a coûté.

C'est exactement le rôle de la classe `fr.utopios.formation.commun.Llm` fournie dans le projet Maven de la formation : elle appelle le serveur Ollama local en HTTP + JSON pur (HttpClient + Jackson, aucun SDK) et expose, après chaque appel, les compteurs de tokens d'entrée et de sortie. Dans ce TP, vous l'utilisez pour faire un appel structuré, lire l'usage tokens, mesurer ce que coûte un long préfixe de contexte, et chiffrer le gain du **prompt caching**.

## Objectifs

- Réaliser un appel LLM structuré via `Llm.chat(prompt, system, temperature)` et lire l'usage tokens (`derniersTokensPrompt()` / `derniersTokensReponse()`).
- Mesurer qu'un préfixe de contexte (message `system`) est recompté en entrée à **chaque** appel — la motivation économique du caching.
- Expliquer la fenêtre de contexte et le prompt caching, et chiffrer leur effet sur le coût (estimation selon réf. prix 2026).

### Étape 1 — Un appel structuré et la lecture de l'usage tokens (20 min)

Objectif : faire un appel via `Llm.chat()` et exploiter les compteurs d'usage.

1. Complétez `etape1AppelStructure()` selon les commentaires du squelette.
2. Relancez. Observez la ligne `[llm] modele=... tokens_prompt=... tokens_reponse=...` : c'est le log de la couche commune sur stderr ; vos propres affichages doivent reprendre ces valeurs via `Llm.derniersTokensPrompt()` / `Llm.derniersTokensReponse()` (chez Ollama : `prompt_eval_count` / `eval_count`).

Point de contrôle : votre programme affiche une réponse en une phrase, le modèle utilisé, et un nombre de tokens d'entrée et de sortie (ordre de grandeur : ~66 tokens d'entrée avec le prompt et le system proposés).

### Étape 2 — Mesurer le coût d'un préfixe de contexte (15 min)

Objectif : constater, chiffres à l'appui, qu'un préfixe stable est recompté en entrée à chaque appel.

1. Complétez `etape2ContextePayeAChaqueAppel()` : même question, system court puis system long (utilisez `String.repeat(50)` pour fabriquer le gros préfixe), température 0.0 pour des réponses stables.
2. Relancez et comparez les deux comptes de tokens d'entrée.

Point de contrôle : la réponse est identique (« Paris. ») dans les deux cas, mais l'entrée passe de quelques dizaines de tokens à plus d'un millier : seul le préfixe gonfle la facture, et il serait refacturé tel quel à chaque nouvel appel.

### Étape 3 — Fenêtre de contexte et prompt caching (20 min)

Objectif : comprendre la fenêtre de contexte et chiffrer le gain du prompt caching.

La fenêtre de contexte est le nombre maximal de tokens (entrée + sortie) qu'un modèle traite en un appel. Référence 2026 : Claude va jusqu'à **1 million de tokens** de contexte. Le **prompt caching** consiste à réutiliser un *préfixe stable* (comme celui de l'étape 2, en beaucoup plus gros) pour ne pas le refacturer plein tarif à chaque requête : écriture ~1,25x au premier appel, lecture ~0,1x ensuite, TTL 5 minutes, minimum cacheable 4096 tokens pour Opus 4.8, tout changement d'un octet invalide le cache.

1. Complétez `etape3EstimationCaching()` selon les commentaires du squelette (attention : la première requête est une écriture à 1,25x, pas une lecture !).
2. Relancez et lisez l'économie obtenue. Pour un préfixe stable réinterrogé souvent, le gain dépasse 80 %.

Point de contrôle : vous obtenez 5,0000 $ sans cache et 0,7875 $ avec cache, soit ~84 % d'économie sur le préfixe. Vous savez expliquer pourquoi, et vous savez quel champ d'usage confirme le cache côté Claude (`cache_read_input_tokens`).

## Dépannage courant

<details>
<summary>Le premier appel est lent</summary>

Cause : Ollama charge le modèle en mémoire au premier appel.
Solution : c'est normal. Les appels suivants sont plus rapides tant que le modèle reste chargé. Vous pouvez pré-charger avec `ollama run llama3.2:1b ""`.

</details>

<details>
<summary>Erreur : `Impossible de joindre Ollama sur http://localhost:11434`</summary>

Cause : le service Ollama ne tourne pas (ou plus).
Solution : vérifiez avec `curl http://localhost:11434/api/tags`. Signalez au formateur si le service ne répond pas.

</details>

<details>
<summary>Erreur Maven : `ClassNotFoundException: fr.utopios.formation.tp.Tp02`</summary>

Cause : le fichier n'est pas au bon endroit ou le nom du package ne correspond pas au dossier.
Solution : le fichier doit être exactement `~/formation/java/src/main/java/fr/utopios/formation/tp/Tp02.java`, avec `package fr.utopios.formation.tp;` en première ligne.

</details>

<details>
<summary>En relançant, le compte de tokens d'entrée de l'étape 2 chute fortement</summary>

Cause : Ollama garde lui-même en mémoire (cache KV) les préfixes déjà traités : un prompt identique relancé peu après peut afficher un `prompt_eval_count` très faible.
Solution : c'est une excellente observation — c'est exactement le principe du prompt caching, appliqué localement par Ollama ! Modifiez un caractère du préfixe pour retrouver le compte complet.

</details>

<details>
<summary>L'économie calculée ne fait pas ~84 %</summary>

Cause classique : le facteur 0,1 appliqué aux 20 requêtes entières, alors que la première est une écriture à 1,25x. Autre confusion : appliquer le cache à la sortie — il ne joue que sur l'entrée.
Solution : coût avec cache = 1 écriture (1,25x) + 19 lectures (0,1x), sur le préfixe uniquement.

</details>
