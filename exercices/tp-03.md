# TP 3 — Bibliothèque de prompts paramétrés et sortie JSON validée

> Module : 3 — Panorama des outils, prise en main et prompt engineering
> Durée estimée : 1h30
> Difficulté : 3 / 5
> Type : Travaux pratiques guidés

## Mise en situation

Un prompt jeté dans un playground ne tient pas en production : il faut des prompts **paramétrés** (réutilisables, versionnables, testables) et des sorties **structurées et validées** pour que le reste du code puisse s'appuyer dessus sans parser du texte libre fragile.

Dans ce TP, vous construisez une petite **bibliothèque de prompts** (gabarits paramétrés) et vous montez en gamme sur les techniques de prompting : zero-shot, few-shot, chain-of-thought. Puis vous forcez le modèle à produire du **JSON**, vous l'extrayez d'une réponse souvent bavarde, et vous le **validez champ par champ avec Jackson**. La validation est la pièce maîtresse : sur un petit modèle local, le format échoue parfois, et c'est précisément pour cela qu'on valide, qu'on réessaie, et qu'on ne renvoie jamais du JSON non vérifié au reste de l'application.

## Objectifs

- Construire des prompts paramétrés réutilisables et comparer zero-shot, few-shot et chain-of-thought sur un même problème.
- Forcer une sortie JSON, l'extraire d'une réponse LLM bavarde, et la valider strictement en Java (types, contraintes, valeurs autorisées) avec Jackson.
- Mettre en place une boucle de re-tentative qui renforce la consigne quand la validation échoue, sans jamais propager une sortie non conforme.

## Architecture cible

```
  GABARIT de prompt parametre  --- replace("{variable}", valeur) --->  prompt concret
            |
            v
   technique de prompting : zero-shot | few-shot | chain-of-thought
            |
            v
        Llm.chat(prompt, null, 0.0)
            |
            v
   reponse BRUTE (souvent bavarde, du texte autour du JSON)
            |
            v
   extraireJson()  -- regex { ... } + Jackson readTree -->  JsonNode
            |
            v
   FicheProduit.valider(node)   <-- validation champ par champ : types + contraintes
       |                       |
   VALIDE -> record type    INVALIDE -> on renforce la consigne et on reessaie
                                        (jusqu'a 3 fois) ; jamais de JSON non verifie
```

## Étapes

### Étape 1 — Monter en gamme sur les techniques de prompting (30 min)

Objectif : comparer trois techniques de prompting sur un même problème de calcul et observer l'effet sur la fiabilité.

1. Lancez le programme de référence du module 3 pour voir le déroulé complet (prompting puis JSON validé) :

   ```bash
   cd ~/formation/java
   mvn -q compile exec:java -Dexec.mainClass="fr.utopios.formation.module03.PromptingEtJson"
   ```

2. Créez `src/main/java/fr/utopios/formation/module03/MonTp03.java` et reconstruisez les trois techniques. Tout tourne en local sur Ollama, donc reproductible et gratuit :

   ```java
   package fr.utopios.formation.module03;

   import fr.utopios.formation.commun.Llm;

   public class MonTp03 {

       public static void main(String[] args) {
           String question = "Marie a 3 boîtes de 4 stylos. Elle en donne 5. "
                   + "Combien lui reste-t-il de stylos ?";

           // 1) Zero-shot : on demande directement.
           System.out.println("[zero-shot]");
           System.out.println("  " + Llm.chat(question).strip());

           // 2) Few-shot : on montre des exemples resolus (le FORMAT attendu).
           System.out.println("\n[few-shot]");
           String few = "Q: J'ai 2 sacs de 3 pommes, j'en mange 1. Combien reste-t-il ? "
                   + "R: 2*3=6, 6-1=5. Réponse: 5\n"
                   + "Q: 4 paquets de 2 gâteaux, j'en donne 3. Combien reste-t-il ? "
                   + "R: 4*2=8, 8-3=5. Réponse: 5\n"
                   + "Q: " + question + " R:";
           System.out.println("  " + Llm.chat(few).strip());

           // 3) Chain-of-thought : on demande explicitement le raisonnement.
           System.out.println("\n[chain-of-thought]");
           String cot = question + " Raisonne étape par étape, puis donne la réponse finale.";
           System.out.println("  " + Llm.chat(cot).strip());
       }
   }
   ```

3. Exécutez (`mvn -q compile exec:java -Dexec.mainClass="fr.utopios.formation.module03.MonTp03"`) et comparez les trois sorties. La bonne réponse est 7 (3 × 4 = 12, puis 12 − 5 = 7). Sur un petit modèle 1b, le zero-shot peut se tromper ou mal formater ; le few-shot fiabilise le *format* ; le chain-of-thought rend le *raisonnement* explicite.

Point de contrôle : vous obtenez trois réponses et vous savez décrire, pour chaque technique, ce qu'elle apporte (format vs raisonnement) et pourquoi le gain est encore plus net sur un gros modèle.

### Étape 2 — Bibliothèque de prompts paramétrés (20 min)

Objectif : transformer un prompt figé en gabarit réutilisable.

1. Ajoutez à `MonTp03.java` une mini-bibliothèque de gabarits paramétrés — une `Map` de gabarits avec des placeholders `{variable}`, et une méthode `rendre` qui injecte les valeurs :

   ```java
   static final java.util.Map<String, String> PROMPTS = java.util.Map.of(
           "resume",
           "Résume le texte suivant en {n} phrases maximum, en français, "
           + "sans introduction.\n\nTEXTE :\n{texte}",
           "traduction",
           "Traduis le texte suivant en {langue}. Ne renvoie QUE la traduction.\n\n{texte}",
           "extraction_mots_cles",
           "Donne exactement {k} mots-clés du texte, séparés par des virgules, "
           + "sans phrase autour.\n\n{texte}");

   /** Rend un gabarit : remplace chaque placeholder {cle} par sa valeur. */
   static String rendre(String nom, java.util.Map<String, String> variables) {
       String gabarit = PROMPTS.get(nom);
       // TODO 1 : si le gabarit n'existe pas, lever une IllegalArgumentException.
       // TODO 2 : pour chaque entrée de `variables`, remplacer "{cle}" par la valeur
       //          (String.replace).
       // TODO 3 (bonus robustesse) : s'il reste un placeholder {…} non remplacé,
       //          lever une IllegalArgumentException plutôt que d'envoyer un prompt troué.
       return gabarit;
   }
   ```

2. Utilisez la bibliothèque sur un texte d'essai :

   ```java
   String texte = "L'IA générative permet d'automatiser la rédaction, mais introduit des "
           + "risques de fuite de données et d'hallucination qu'il faut encadrer.";

   System.out.println("\n[resume]");
   System.out.println("  " + Llm.chat(
           rendre("resume", java.util.Map.of("n", "1", "texte", texte)), null, 0.0).strip());

   System.out.println("\n[extraction_mots_cles]");
   System.out.println("  " + Llm.chat(
           rendre("extraction_mots_cles", java.util.Map.of("k", "3", "texte", texte)),
           null, 0.0).strip());
   ```

3. Exécutez. Vous disposez désormais d'une bibliothèque de prompts que l'on peut versionner, tester et réutiliser, en injectant des variables au lieu de réécrire le texte.

Point de contrôle : vos gabarits produisent des réponses cohérentes avec les paramètres (nombre de phrases, nombre de mots-clés). Vous comprenez l'intérêt de séparer le *gabarit* du prompt de ses *valeurs*.

### Étape 3 — Sortie JSON structurée et validée avec Jackson (40 min)

Objectif : forcer du JSON, l'extraire, le valider strictement, et réessayer proprement.

1. Ajoutez le schéma cible (un `record`) et les fonctions d'extraction / validation à `MonTp03.java`. La validation champ par champ est l'équivalent Java du schéma pydantic côté Python : chaque champ est vérifié (présence, type, contrainte) avant de construire l'objet typé :

   ```java
   import com.fasterxml.jackson.databind.JsonNode;
   import com.fasterxml.jackson.databind.ObjectMapper;
   import java.util.Set;
   import java.util.regex.Matcher;
   import java.util.regex.Pattern;

   static final ObjectMapper MAPPER = new ObjectMapper();

   /** Schema cible : la reponse du LLM DOIT s'y conformer. */
   record FicheProduit(String nom, String categorie, double prixEur, boolean enStock) {

       static final Set<String> CATEGORIES_AUTORISEES =
               Set.of("informatique", "maison", "sport", "alimentaire", "autre");

       /** Valide un JsonNode champ par champ et construit l'objet type. */
       static FicheProduit valider(JsonNode n) {
           // TODO 1 : verifier que "nom" existe, est textuel et non vide,
           //          sinon lever IllegalArgumentException("champ 'nom' manquant ou vide").
           // TODO 2 : verifier que "categorie" existe et est textuelle.
           // TODO 3 : verifier que "prix_eur" existe, est numerique et >= 0.
           // TODO 4 : verifier que "en_stock" existe et est un booleen.
           // TODO 5 : normaliser la categorie en minuscules ; si elle n'est pas dans
           //          CATEGORIES_AUTORISEES, la remplacer par "autre" (on normalise
           //          plutot que de planter : robustesse).
           return new FicheProduit(n.get("nom").asText(),
                   n.get("categorie").asText().toLowerCase(),
                   n.get("prix_eur").asDouble(),
                   n.get("en_stock").asBoolean());
       }
   }

   /** Extrait le premier objet JSON d'une reponse LLM (souvent bavarde). */
   static JsonNode extraireJson(String texte) {
       Matcher m = Pattern.compile("\\{.*\\}", Pattern.DOTALL).matcher(texte);
       if (!m.find()) {
           throw new IllegalArgumentException("Aucun JSON trouvé dans la réponse du modèle.");
       }
       try {
           return MAPPER.readTree(m.group());
       } catch (Exception e) {
           throw new IllegalArgumentException("JSON invalide : " + e.getMessage());
       }
   }
   ```

2. Ajoutez la boucle de génération + validation + re-tentative :

   ```java
   String prompt = "Extrais une fiche produit de ce texte et réponds UNIQUEMENT en JSON "
           + "avec les clés exactes : nom (string), categorie (string parmi "
           + "informatique/maison/sport/alimentaire/autre), prix_eur (number), "
           + "en_stock (boolean). Pas de texte autour.\n\n"
           + "Texte : « Le clavier mécanique AZERTY Pro est dispo à 89,90 € et "
           + "actuellement en stock. C'est un accessoire informatique. »";

   Exception derniere = null;
   boolean valide = false;
   for (int tentative = 1; tentative <= 3 && !valide; tentative++) {
       String r = Llm.chat(prompt, null, 0.0);
       System.out.println("\n[tentative " + tentative + "] réponse brute : "
               + r.strip().substring(0, Math.min(r.strip().length(), 200)));
       try {
           FicheProduit fiche = FicheProduit.valider(extraireJson(r));
           System.out.println("VALIDATION Java : OK -> " + fiche);
           valide = true;
       } catch (IllegalArgumentException exc) {
           derniere = exc;
           System.out.println("Validation échouée : " + exc.getMessage());
           prompt += "\n\nRappel : réponds STRICTEMENT en JSON valide, rien d'autre.";
       }
   }
   if (!valide) {
       System.out.println("Échec après 3 tentatives. Dernière erreur : " + derniere);
       System.out.println("-> En prod : on rejette, on logge, ou on passe à un modèle plus fort,");
       System.out.println("   ou on utilise les sorties structurées natives de l'API (Claude/Mistral).");
   }
   ```

3. Exécutez plusieurs fois. Observez : parfois la première tentative valide directement, parfois il faut une ou deux re-tentatives. La clé pédagogique : **on ne renvoie jamais** au reste du programme un JSON qui n'a pas passé `FicheProduit.valider`.

4. Testez la robustesse du schéma : validez à la main un JSON où `categorie` vaut une valeur hors liste (par exemple `"jardinage"`, via `MAPPER.readTree("{...}")`) et vérifiez que votre validation la normalise en `"autre"` au lieu de lever une exception.

Point de contrôle : vous obtenez un `record FicheProduit` typé et valide, ou un échec explicite après 3 tentatives. Vous savez expliquer pourquoi la validation est indispensable, et vous citez l'alternative côté API (sorties structurées natives : `messages.parse(... output_format=...)` côté Claude, JSON mode côté Mistral, réf. 2026).

## Dépannage courant

<details>
<summary>La validation échoue à chaque tentative</summary>

Cause : le petit modèle local n'arrive pas à respecter le schéma (clé manquante, type incorrect).
Solution : c'est un comportement attendu et instructif. Augmentez le nombre de tentatives, renforcez la consigne (clés exactes, exemple de sortie), gardez la température à 0.0, ou basculez sur un provider cloud avec une clé. En prod, c'est exactement le moment où l'on choisit les sorties structurées natives de l'API.

</details>

<details>
<summary>`JSON invalide` alors qu'il y a bien des accolades</summary>

Cause : le modèle a produit du JSON quasi valide mais avec une virgule finale, des guillemets typographiques, ou plusieurs objets.
Solution : la regex `\{.*\}` capture le premier bloc le plus large. Si le modèle renvoie plusieurs objets, resserrez la consigne (« un seul objet JSON »). Demandez explicitement des guillemets droits.

</details>

<details>
<summary>Un placeholder `{...}` reste dans le prompt envoyé</summary>

Cause : une variable du gabarit n'a pas été fournie à `rendre(...)`.
Solution : vérifiez que tous les `{...}` du gabarit correspondent à des clés de la `Map` passée à `rendre`. Le TODO 3 de l'étape 2 (détection des placeholders restants) transforme ce bug silencieux en erreur explicite.

</details>
